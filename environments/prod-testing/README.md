# prod-testing

Settings of the multi-node production-like test environment used for the 1-million-farmer load tests
(November 2026): Commons + farmer registry on RKE2, host PostgreSQL with a streaming replica and PgBouncer,
MinIO on its own VM, observability on its own node. Domain `ati-uat.oanstaging.com`.

No secrets are kept here. Every chart and manifest references Secrets that are created beforehand, by name.

## Topology

| Node | Size | Role |
|---|---|---|
| rke2-cp-01 | 16 vCPU / 64 GiB | RKE2 server, Istio ingress, Rancher, monitoring |
| farmer-app-01 | 16 vCPU / 32 GiB | farmer pool (`openg2p.org/pool=farmer`, taint `pool=farmer:NoSchedule`) |
| farmer-app-02, -03, -04 | 8 vCPU / 16 GiB each | farmer pool (same label and taint) |
| commons-app-01 | 16 vCPU / 64 GiB | Commons pool |
| odk-central-01 | 8 vCPU / 32 GiB | ODK pool |
| observability-01 | 8 vCPU / 64 GiB | observability pool (Prometheus, Grafana, Loki) |
| pg-primary-01 (VM) | 64 vCPU / 128 GiB | PostgreSQL 16 primary + PgBouncer + NFS |
| pg-replica-01 (VM) | 8 vCPU / 64 GiB | PostgreSQL 16 streaming replica |
| minio-01 (VM) | 8 vCPU / 32 GiB | MinIO |

Namespace placement is enforced by the API server (`PodNodeSelector` + `PodTolerationRestriction`, see
`manifests/namespaces.yaml`): pods in `farmer` can only land on farmer-pool nodes, `commons` on commons-app-01.

`values/*-gateways.yaml` are generated by `tools/gateway-overlay.py`; they move every Istio VirtualService from the
chart's `istio-system/development` gateway to this environment's `test/internal`.

```sh
helm upgrade --install farmer-registry charts/openg2p-farmer-registry -n farmer \
  -f environments/prod-testing/values/farmer-gateways.yaml \
  -f environments/prod-testing/values/farmer.yaml
```

## Farmer registry settings (from the load tests)

All in `values/farmer.yaml`:

| Setting | Value | Why |
|---|---|---|
| Staff API | request 1500m CPU / 595Mi, limit 1536Mi memory, no CPU limit | a pod uses ~3 cores under load; CPU request is the autoscaler's baseline |
| Partner API | request 1500m / 640Mi, limit 1280Mi | |
| Celery worker | request 1500m CPU / 1Gi, limit 1600Mi memory (measured peak 767 MB per pod); `CELERY_OPTS` 4 processes, prefetch 1, fresh process per task, 1.5 GB per process, 600/660 s time limit | 0 out-of-memory kills under backlog (was 115 in 9 h with 16 processes); fresh process works around the shared-event-loop bug |
| Celery worker AWE | `REGISTRY_CELERY_WORKERS_AWE_*` | the chart leaves AWE off in the worker; intakes never reach approval without it |
| DB port 6432 (staff API, partner API, beat, worker) | HAProxy `:6432` → PgBouncer | connection pooling; halves database CPU per request together with the role settings |
| DB pool per worker process (staff API, partner API, beat, worker) | `DB_POOL_SIZE` 5 + `DB_POOL_MAX_OVERFLOW` 10 = up to 15 connections; 3 processes per API pod → 45 per pod | values as running (chart defaults, recorded); PgBouncer caps PostgreSQL at 80 farmer connections |
| `autoscaling.*` (chart template `autoscaling.yaml`) | staff API 1–5, partner API 1–3, Celery 1–4, at 70% CPU; +1 pod/min, −1 pod/2 min after 5 min | each new API pod runs the startup migration (~60 s exclusive lock on the farmers table) |
| `dbSettings` (chart template `db-settings.yaml`) | trigram index `idx_g2p_register_farmers_search_text_trigram`; `plan_cache_mode=force_custom_plan`, `idle_in_transaction_session_timeout=60s`, `max_parallel_workers_per_gather=0` for `farmer_registry_user` | search 1.3–1.4 s → 0.08–0.3 s; browse kept on a table scan; a stuck request can't hold the table locked; −31% DB CPU per request |
| Images | pinned to the tested build `90811b61a59f` | reproduces the tested state; reporting views stay off until an image bump |

**Not settable through the chart:** the Celery worker's `terminationGracePeriodSeconds` (720 s, longer than the
660 s task limit, so a scale-down lets running tasks finish). The pinned openg2p-registry subchart has no key for it.
After install:

```sh
kubectl -n farmer patch deploy farmer-registry-celery-worker --type=merge \
  -p '{"spec":{"template":{"spec":{"terminationGracePeriodSeconds":720}}}}'
```

**Before a `helm upgrade` of an existing install:** remove HPAs that were created by hand with the same names
(`kubectl -n farmer delete hpa farmer-registry-staff-portal-api farmer-registry-partner-api farmer-registry-celery-worker`).
Helm will not adopt them. Also note that the chart's install hooks (keycloak-init, postgres-init, idgen-pg-init, db-seed,
sanity) run again on upgrade.

## Outside Kubernetes (reference copies)

| File | What |
|---|---|
| `manifests/` | kubectl-applied: namespaces and placement, Commons aliases, split-horizon DNS, HAProxy `db-proxy` (`:5432` read-write, `:5433` read-only, `:6432` PgBouncer), Services/Endpoints for the VMs, MinIO route, exporters, alerts, Grafana dashboards and route, observability storage and VM log intake |
| `hosts/pgbouncer/` | PgBouncer 1.22 on the primary: transaction pooling, `max_prepared_statements` 200, pool 60 + 10 reserve, `max_db_connections` 80, `max_client_conn` 2000. `userlist.txt` is generated on the host from `pg_authid` and is not kept here |
| `hosts/pg-role-check.py` | `/primary` and `/replica` health endpoint on :8008 that HAProxy uses to route |
| `hosts/farmer-search-trigram-index.sql` | the search index as plain SQL, for a database restored outside Helm (the chart's `dbSettings` Job does the same) |

PostgreSQL 16 on the primary (`ALTER SYSTEM`):
- **Memory:** `shared_buffers` 16 GB with huge pages, `effective_cache_size` 44 GB, `work_mem` 16 MB, `maintenance_work_mem` 1 GB.
- **Parallelism and maintenance:** `max_worker_processes` / `max_parallel_workers` 64 (also on the replica, which must be ≥ the primary), `max_parallel_maintenance_workers` 8, `autovacuum_max_workers` 6.
- **Other:** `jit` off, `wal_compression` lz4, `max_connections` 300.
- **Kernel:** `vm.overcommit_memory` 2 (ratio 80), swappiness 10.
- **Per-table autovacuum:** 2% / 1% on the 11 busiest farmer tables, 5% / 2% on the AWE tables.
